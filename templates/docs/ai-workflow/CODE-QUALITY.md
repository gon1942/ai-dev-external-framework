# AI 개발 코드 품질 및 파일 분리 지침

> 적용 대상: OpenCode · Codex · Claude Code  
> 적용 단계: Analyze · Plan · Implement · Verify · Review

## 1. 기본 원칙

에이전트는 기능의 정상 동작뿐 아니라 유지보수 가능한 코드 구조를 보장해야 한다.

- 하나의 파일에 여러 책임을 집중시키지 않는다.
- 기존 파일에 기능을 무조건 추가하는 방식을 피한다.
- 신규 기능은 기존 코드와의 책임 경계를 먼저 분석한다.
- 공통 로직은 적절한 모듈로 분리한다.
- 단순한 코드 분량 축소를 위한 불필요한 파일 분할은 금지한다.
- 기능을 여러 파일로 나누더라도 인터페이스와 의존성은 명확하게 유지한다.
- 기존 동작을 보존하고 구조 변경에 따른 회귀 테스트를 수행한다.

## 2. 코드 크기 및 복잡도 기준

다음 수치는 초기 권장 기준이며 프로젝트의 언어·파일 종류에 맞게 조정할 수 있다.

| 항목 | 권장 기준 | 초과 시 조치 |
|---|---|---|
| 일반 소스 파일 | 300줄 이하 권장 | 책임 분리 검토 |
| 소스 파일 500줄 초과 | 구조 검토 필수 | 분리 또는 예외 근거 기록 |
| 함수·메서드 | 50줄 이하 권장 | 책임 및 로직 분리 검토 |
| 함수·메서드 100줄 초과 | 구조 검토 필수 | 분리 또는 예외 근거 기록 |
| 순환 복잡도 | 15 이하 권장 | 조건문·분기 구조 개선 검토 |
| 중첩 깊이 | 4단계 이하 권장 | 조기 반환·책임 분리 검토 |

줄 수만으로 품질을 판정하지 않는다. 생성 코드, 선언형 설정, 스키마 정의, 대규모 상수·타입 선언 등에는 예외를 둘 수 있다.

수치 기준 초과는 자동으로 오류를 의미하지 않지만, 검토 없이 방치해서는 안 된다.

## 3. Plan 단계 — 사전 구조 설계

에이전트는 구현 계획 작성 시 다음을 확인한다.

1. 신규 기능을 담당할 모듈과 파일의 책임
2. 기존 소스 파일의 규모와 복잡도
3. 기존 파일 확장과 신규 모듈 분리 중 적합한 방식
4. 변경될 API·함수·타입·데이터 흐름
5. 구조 변경으로 영향을 받는 테스트

기존 소스 파일이 이미 과도하게 크다면 기능 추가 전 책임 분리 가능성을 검토한다.

단, 요청 범위와 관련 없는 대규모 리팩터링은 수행하지 않는다.

## 4. Implement 단계 — 구현 중 파일 비대화 방지

에이전트는 코드를 작성하면서 파일의 책임과 규모를 점검한다.

다음 상황에서는 모듈 분리를 우선 검토한다.

- 하나의 파일에 서로 다른 업무 기능이 추가되는 경우
- HTTP 요청 처리, 비즈니스 로직, 데이터 접근 로직이 한 파일에 섞이는 경우
- 동일한 코드가 여러 곳에서 반복되는 경우
- 하나의 함수가 여러 단계의 작업을 모두 처리하는 경우
- 기존 기능을 수정할 때 관련 없는 코드까지 함께 변경해야 하는 경우
- 테스트가 어려울 정도로 파일 간 결합도가 높아지는 경우

모듈 분리가 필요한 경우에는 각 파일의 역할과 인터페이스를 정의한다.

이미 승인된 작업 범위를 넘어서는 구조 변경이 필요한 경우 사용자에게 변경 필요성과 영향을 보고한다.

## 5. Verify 단계 — 구조 및 기능 검증

에이전트는 기능 테스트와 코드 구조 검사를 구분하여 수행한다.

검증 항목:

1. 신규·변경 파일의 줄 수 확인
2. 변경 함수의 크기와 복잡도 확인
3. 중복 로직과 불필요한 책임 집중 확인
4. 모듈 분리 후 import 및 의존성 확인
5. 기존 기능에 대한 회귀 테스트 수행
6. 인수 조건(AC) 충족 여부 확인

구조 검사 도구가 설치되어 있지 않다면 이를 보고하고, 가능한 범위에서 수동 검토한다.

도구를 실행하지 않았는데 구조 검사를 완료했다고 보고하지 않는다.

## 6. Review 단계 — 독립적인 구조 검토

코드 리뷰에서는 기능 정상 동작 외에 다음 항목을 검토한다.

- 기능별 책임 분리가 적절한가?
- 하나의 파일이 너무 많은 역할을 담당하는가?
- 새 코드가 기존 구조의 복잡성을 불필요하게 증가시키는가?
- 파일 분리가 오히려 과도한 추상화를 유발하는가?
- 테스트 가능성과 유지보수성이 개선되었는가?
- 기능 추가에 따라 기존 코드의 결합도가 높아지지 않았는가?

코드 크기·복잡도 기준을 초과한 항목은 수정 여부와 예외 사유를 리뷰 결과에 기록한다.

## 7. 예외 및 승인

다음은 예외를 허용할 수 있다.

- 자동 생성 코드
- 외부 라이브러리 원본
- 스키마 및 타입 선언 중심의 파일
- 단순 데이터·상수 정의 파일
- 구조 변경 시 오히려 유지보수성이 악화되는 경우

예외는 대상 파일, 기준 초과 내용, 유지 사유를 기록한다.

예외가 보안·검증·승인 원칙을 완화해서는 안 된다.

## 8. 완료 보고

구현 또는 리뷰 단계 종료 시 필요한 경우 다음 항목을 보고한다.

- 생성·변경된 주요 파일
- 구조 변경 또는 모듈 분리 여부
- 크기·복잡도 기준 초과 항목
- 초과 항목의 조치 결과 또는 예외 사유
- 관련 테스트 및 검증 결과
- 남은 구조 개선 작업

**기능 구현 완료와 코드 구조 적정성 검토 완료를 구분하여 보고한다.**
