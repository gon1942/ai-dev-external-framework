# 단계별 사용자 보고 표준 (Stage Report Contract)

이 문서는 **OpenCode · Codex · Claude Code가 공통으로 따라야 하는 사용자 안내 형식**입니다. 원본 외부 스킬을 수정하지 않습니다. 세 에이전트는 이 지침을 읽고 실제 출력 메시지에 반영합니다. 단순히 작업 파일에 기록하는 것만으로 사용자 안내를 완료한 것으로 간주하지 않습니다.

## 공통: 각 단계가 끝날 때 반드시 사용자에게 표시

1. **작업 ID · 현재 단계 · 판정**: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`, `NEEDS_APPROVAL` 중 실제 확인된 상태. 부분 완료는 PASS로 표시하지 않습니다.
2. **완료한 일**: 변경 파일/기능, 근거가 되는 작업 파일 경로, 실행한 스킬(선택 사유와 실제 호출 여부를 구분).
3. **검증된 사실과 미검증 사항**: 실제 실행한 명령, 관찰 결과, 근거 파일 경로. 실행하지 않은 검사는 `NOT_RUN`으로 표시합니다.
4. **남은 작업**: 완료 조건까지 필요한 작업을 우선순위 순서대로 정리하고, `담당: 에이전트/사용자/외부`, `진행 상태`, `막힘 여부`를 표시합니다. 남은 작업이 없으면 `남은 작업 없음`이라고 명시합니다.
5. **다음 단계와 사용자 행동**: 사용자가 해야 할 구체적인 결정·승인·입력·환경 준비를 하나의 명확한 요청으로 제시합니다. 사용자 행동이 필요 없으면 `사용자 조치 불필요 — 에이전트가 다음 단계 진행`으로 밝힙니다. 실제 사용자 승인 전에는 승인된 것으로 기록하지 않습니다.

작업을 진행하는 도중에도 **중요 오류, 새로운 위험, 승인 필요 상태**가 생기면 즉시 안내합니다. 정상적인 연속 작업마다 사소한 진행 사항을 반복 출력하지는 않습니다.

## 단계별 필수 상세 보고

| 단계 | 상세히 보고할 정보 | 사용자에게 요청할 행동 |
| --- | --- | --- |
| Analyze | 요청을 어떻게 이해했는지, 현행 동작/재현 조건, 분석 근거, 범위·제약, 미확정 질문, 후보 접근과 추천 이유 | 필수 요구·범위가 모호할 때만 확인 요청. 바로 답할 수 있는 분석은 계속 진행 |
| Plan | 구현·제외 범위, 변경 예정 파일, 주요 작업/의존성, AC 목록과 테스트 매핑, 위험/대안, 예상 검증 방법, 미결정 항목 | **계획 승인 / 수정 요청**을 구체적으로 안내. 승인 없으면 Implement 진행 금지 |
| Implement | 실제 변경 파일과 핵심 동작, 계획 대비 구현 완료율(분모 명시), 추가/변경된 테스트, 미완료 항목 및 기술적 위험 | 새 범위 결정 필요 시에만 승인 요청. 구현 완료가 Verify 통과를 뜻하지 않음 |
| Verify | **AC별 표**: AC ID, 기대 결과, 실제 실행 명령, PASS/FAIL/NOT_RUN, 관찰 결과, 증거 로그 경로·실행 시점, 현재 소스에 대한 증거 최신성. 실패·스킵·커버리지 부족 목록과 재검증 계획 | 사용자 환경/계정/시나리오가 필요한 항목만 구체적으로 요청. FAIL 또는 미검증 항목이 남으면 검증 완료 선언 금지 |
| Review | **심각도별 발견 사항**: Critical/High/Medium/Low, 문제 위치, 영향, 근거, 수정 여부, 재검증 여부. 범위 외 위험과 남은 개선 작업, 리뷰의 독립성 확인 가능 여부, 리뷰 판정 PASS/FAIL | 해결 방법·위험 수용 등 사용자 결정이 필요한 경우 명시. 단순 PASS 판정만 제시하지 않음 |
| Complete | 변경·검증·리뷰 결과 종합, 모든 AC의 현 상태, 남은 위험/이월 작업, 최종 산출물 경로, 완료 기준 충족 여부 | **최종 완료 승인 / 보류**를 명확히 요청. 승인 전 `workflow.py complete` 호출 금지 |

## 검증(Verify) 보고 예시

```text
작업: TASK-LOGIN-001 | VERIFY | BLOCKED
검증 환경: Linux / Node.js 22 (실제로 확인된 경우만 기입)
AC-01 로그인 성공 | PASS    | npm test -- login-success | evidence.jsonl / logs/....log
AC-02 비밀번호 오류 | FAIL   | npm test -- login-fail    | logs/....log (기대 코드와 불일치)
AC-03 브라우저 동작 | NOT_RUN| Playwright 실행 안 함      | 증거 없음
남은 작업:
- [에이전트 / 진행 필요] AC-02 결함 수정 후 테스트 재실행
- [사용자 / 입력 필요] AC-03 테스트 계정 제공 여부 결정 (실제 필요할 때만)
다음 단계: AC-02 재구현·재검증; 검증 통과 전 리뷰 PASS/완료 불가
```

## 리뷰(Review) 보고 예시

```text
작업: TASK-LOGIN-001 | REVIEW | FAIL
검토 범위: 변경 파일 4개, 관련 AC 3개
High: 로그인 실패 시 내부 오류 정보 노출 | src/auth.ts:120 | 수정 필요
Medium: 타임아웃 경계 사례 테스트 누락 | tests/auth.test.ts | 테스트 추가 필요
수정 완료: 없음 / 재검증: NOT_RUN
남은 작업: [에이전트] 보안 오류 수정 → 관련 테스트 재실행 → 재리뷰
사용자 조치: 현재 없음. 변경 범위 확대가 필요하면 승인 요청 예정
```

위 두 예시는 **형식 안내용 가상 데이터**입니다. 실제 보고에는 확인된 근거만 사용하고, 로그 경로나 파일 위치를 만들어내지 않습니다.

## 증거와 사용자 승인 경계

- `workflow.py gate` 통과는 명령·파일·소스 지문에 대한 **구조적 조건**을 확인할 뿐, AC가 실제 업무 요구를 충분히 검증했는지 또는 리뷰가 독립적이었는지 보증하지 않습니다.
- 테스트 증거는 `docs/exec-plans/active/TASK-ID/evidence.jsonl`, `logs/`; 리뷰 근거는 `reviews/`를 참조합니다. 존재하지 않으면 `없음`이라고 표시합니다.
- `using-superpowers`의 스킬 선택은 작업 실행을 도울 뿐 호출 증거를 자동 생성하지 않습니다.
- 계획 승인과 완료 승인은 **별개**입니다. 에이전트가 사용자를 대신해 승인하지 않으며, 사용자가 명시적으로 승인한 경우에만 `--user-confirmed`를 사용합니다.
- 보고서는 **현재 작업 상태를 요약**해야 합니다. `PASS`, `FAIL`, `BLOCKED`와 `NOT_RUN`을 섞어서 하나의 '완료'로 표현하지 않습니다.
